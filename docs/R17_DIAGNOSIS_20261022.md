## 1. 背景与范围

本轮收到两个相互独立的故障现象，必须分开定性，不能混为一谈：

- **故障 A（shell 不可用）**：另一个跑在 **web profile** 的 DSH 会话里，每次执行
  shell 命令立即退出，退出码 `3221225794`（`0xC0000142` = `STATUS_DLL_INIT_FAILED`，
  Windows 进程加载器在 DLL 初始化阶段失败），零输出、零等待；文件读取工具仍可用，
  模型仍能响应。现场截图：4 次命令（`Check node/pnpm and dsh CLI availability`、
  `Print working directory`、`Smoke-test shell execution`、`Check workspace path exists`）
  全部退出 `3221225794`；顶部提示「工具已更新·移除 28 个」。
- **故障 B（gaussian 被关闭 + bundles 缺口）**：**desktop profile** 里 gaussian 插件被
  `disabled: true` 显式关闭；aifs、autorest 在 `dependencies` 但不在 `dsh.profile.bundles`。

用户疑问：「是不是 gaussian 插件把 DSH 搞坏了」。本文件第 3、4 节给出基于证据的责任归属。

## 3. 故障 A：shell 退出码 0xC0000142

### 3.1 调用链还原（解包 `E:\DSH\resources\app.asar` 实证）

一次性命令工具与常驻 PTY 终端是两条不同链路；故障 A 属于一次性命令链路：

```
dsh-tool-pwsh（工具注册/参数校验/结果渲染）
  → ctx.shell.resolve / ctx.shell.execute
  → dsh-pwsh-local（PwshLocalExecutor：解析 pwsh 路径、拼 argv、组 spawnSpec）
  → dsh-subprocess-local（spawnSubprocess / Windows runner bootstrap）
  → runner 独立 Node 子进程（spawnRunnerInvocation，打包态 = process.execPath）
  → dsh-win32-process：koffi 绑定 CreateProcessW（挂起创建 → AssignProcessToJobObject → ResumeThread）
  → 目标进程：powershell.exe 5.1（本机未装 PowerShell 7，回退路径）
```

关键源码位置（解包副本 `docs/_dsh_unpack/dsh/`）：

- `@deepseek-ai/dsh-pwsh-local/lib/index.js:23–64` `candidatePwshPaths` / `resolvePwshPath`：
  候选顺序 `ProgramFiles\PowerShell\7\pwsh.exe` → 遍历 PATH 各目录 `pwsh.exe` →
  `SystemRoot\System32\WindowsPowerShell\v1.0\powershell.exe`；三者都不存在才回退裸 `"pwsh"`。
- 同文件 `:197–205` `argv(spec)`：`[pwshPath, "-NoLogo", "-NoProfile", "-NonInteractive", "-Command", ENCODING_PREAMBLE + command]`。
- 同文件 `:208–228` `spawnSpec`：`cwd=spec.workdir`；`env={...ENV_OVERRIDES, ...spec.env, ...spec.dshEnv}`，
  ENV_OVERRIDES 为 NO_COLOR/PAGER/GIT_PAGER。
- 同文件 `:306` `this.ctx.subprocess.spawn(...)`。
- `@deepseek-ai/dsh-subprocess-local/lib/runner-launch-B2zsQ1Dz.js:694–707` `childEnv(extra)`：
  `scrubbedParentEnv()` 全量继承父环境，Windows 分支按大小写不敏感合并 extra；
  `scrubbedParentEnv()` 仅剔除键名匹配 `/KEY|PASSWORD|SECRET|TOKEN/i` 与 `DSH_` 前缀，
  SystemRoot/ComSpec/windir/PATH 全部保留。
- 同文件 `:1020–1039` `spawnSubprocess`：`env=controlEnvironment(childEnv(spec.env), ...)`，
  **父环境保留后再合并 spec.env，不是整体替换**。
- 同文件 `:1310–1321` `spawnRunnerInvocation`：打包态（`"pkg" in process`）返回 `[process.execPath]`；
  `:1343–1356` `runnerEnvironment`：`childEnv()` 后删除 NODE_/TSX_ 前缀，写入
  `DSH_SUBPROCESS_RUNNER=windows`。
- `@deepseek-ai/dsh-win32-process/lib/index.js:382–385` `encodeWindowsEnvironment`：
  `KEY=VALUE` 以 `\0` 连接、末尾 `\0\0`、转 utf16le，格式符合 Windows 环境块规范。
- 同文件 `:537–547` `createKillOnCloseJob`：Job 限制仅 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`(0x10)，
  **无内存上限、无进程数上限**。
- 同文件 `:584–679` `spawnJobProcess`：挂起创建（`dwCreationFlags=0x404=CREATE_SUSPENDED|CREATE_UNICODE_ENVIRONMENT`）
  → `AssignProcessToJobObject` → `ResumeThread`；`:701–704` `spawnCurrentTokenJobProcess`
  使用**当前普通 token**（非受限 token），`CreateProcessW(..., bInheritHandles=1, ...)`。

### 3.3 未排除 / 待实机复现项（诚实标注，不跨层下结论）

以下方向本轮**没有本机运行证据**，不能断言已排除，也不能写成本机已确诊根因：

- **B1（首要候选，有官方包文档机制佐证）：会话级受限沙箱模式（read-only / workspace-write）**。
  官方包 `@deepseek-ai/dsh-sandbox-windows-acl` README 明确：受限令牌下用 `CREATE_NO_WINDOW` /
  `CREATE_NEW_CONSOLE` 创建的子进程会在 DLL 初始化阶段死亡，报 `STATUS_DLL_INIT_FAILED`
  （0xC0000142）；`read-only` 与 `workspace-write` 两种模式都把 pwsh 放进 ConstrainedLanguage，
  `danger-full-access` 不套沙箱、走 FullLanguage。社区问题库（dsh-ai.com FAQ，2026-10-13 更新）
  收录多条同类 Windows 复现：#10010、#9621、#9858、#9682、#9507、#8721、#8485、#8395、#8784、
  #6930，主题均为 workspace-write/read-only 受限沙箱 shell 全报 0xC0000142；其中 #8485 注明
  read-only 与 danger-full-access 正常、workspace-write 存在缺陷，#8395 在 0.2.0-rc.2 已解决。
  **待实机核对**：故障会话当时在权限选择器选的是哪一档；截图标题栏"工具已更新·移除 28 个"与
  只读提示需对照会话权限状态确认。若当时为受限档位，本机现象与该已知缺陷吻合；切到
  `danger-full-access` 能临时绕开，但这是放宽安全边界，不是根治，也不属于自研插件修复范围。
  证据等级：官方包 README 机制为一手；issue 编号来自社区问题库索引，未逐条打开 GitHub 原文核验。
- **B2（分层未决）**：0xC0000142 发生在 runner bootstrap（独立 Node 子进程）自身启动阶段，还是
  runner 内经 koffi `CreateProcessW` 拉起的 powershell.exe 初始化阶段——两者退出码都会被
  `outcome.exitCode` 透传给工具层，仅看 `3221225794` 无法区分。需要在 DSH 内实发一条命令时
  抓 runner 侧 stderr/startup-error 与子进程 PID 才能分层。
- **B3**：koffi 原生绑定在 host 内加载/调用上下文异常（`requireKoffi` 懒加载、绑定表初始化）；
  本轮未在 DSH 同款 koffi Job Object 上下文内实机复现 0xC0000142（Node 原生 spawn ≠ koffi
  CreateProcessW，复现脚本只证明 Node 侧链路健康，不能顶替 koffi 链路证据）。
- **B4**：瞬时 loader/桌面堆状态、Defender 被策略禁用后的系统安全基线残留、user32/某注入 DLL
  初始化失败等运行时因素；需要 WER/Application 事件、Procmon 进程创建轨迹佐证。本轮 WER
  ReportArchive 无本次 shell 子进程 APPCRASH（loader 阶段退出不触发 WER 收集），Application 日志
  15:44:45、15:45:52 两条 1000/1001 正文为空，无法据此定案。host 进程 26244 实际环境块（PEB）
  未逐字节读取；源码链已证明无丢失点，但未做 PEB 实证。

### 3.4 故障 A 责任归属结论

- 与 `@gaussian/dsh-plugin-gaussian` **没有因果关系**：故障会话跑在未安装任何插件的 web profile；
  gaussian 后端独立、未启动；插件 lib/exe 哈希与 R16 终态一致、文件未损坏。
- 故障域属于 **DSH 内置一次性 shell 子系统**（`dsh-tool-pwsh` / `dsh-pwsh-local` /
  `dsh-subprocess-local` runner / `dsh-win32-process` koffi 链路）或本机运行时环境，
  不在自研插件源码范围内；首要方向是会话级 read-only / workspace-write 受限沙箱在 Windows 上的
  已知 0xC0000142 缺陷（见 3.3 B1 与官方 `@deepseek-ai/dsh-sandbox-windows-acl` README 机制）。
- 当前 16:55 重启后的 desktop 会话 shell 是否仍复现 0xC0000142，属于**待现场观察项**：
  本 Doubao 会话持独立 PowerShell 工具，无法触发 DSH host 内的 shell 子系统，不能代替实机结论。

## 4. 故障 B：gaussian `disabled: true` 与 bundles 一致性缺口

### 4.1 写入来源取证（解包 `@deepseek-ai/dsh-plugin-manager` 实证）

- `disabled` 开关在 profile `cordis.patch.yml` 的唯一写入函数是 `writePluginEnabled(profile, id, name, enabled)`，
  由 UI 拨开关时的 `setPluginEnabled(id, enabled)` 调用（操作 stage 为 `"enable"`）。
- **源码中不存在「entry 激活失败后框架自动写 disabled」的路径**；激活失败只会产生黄条/崩溃日志，
  不会回写 patch 层关闭开关。
